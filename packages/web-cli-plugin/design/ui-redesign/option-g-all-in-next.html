    ① NextProvider 插件注册表 —— 新增操作 = 注册插件 + 自带测试，主流程零改动

    每个 provider 是 {id, priority, when(ctx)→候选|null, chips[]}。when 是纯谓词（给定 ctx 返回布尔）， 因此可以单测、可以组合、可以并行求值；chips 只是 opId 列表，渲染与点击都由通用管线接管。

    // 新增一个「操作」= 注册一个 provider（唯一改动点） registry.push({ id: 'perm.request', priority: 1, // 0 恢复 / 1 引导 / 2~3 发现 when: ctx => ctx.site.authorized && !ctx.perm.granted, // 纯谓词，可单测 chips: ['op.perm.request'] }); // handleCardAction：只有一次查表，没有任何 per-op 分支 —— 所以 diff 恒为 0 function handleCardAction(opId) { const op = OPS_BY_ID[opId]; // OPS 是 op 清单（下节） return op ? op.execute() : false; // 分发器不含任何操作的特例代码 }

    本稿注册表初始 8 个 provider（恢复 3 / 引导 3 / 发现 2）；点演示控制台里的 「注册演示 provider」即 N→N+1，而 handleCardAction 分发器 diff = 0（活体可视化见顶部「注册表视察器」）。

    • 恢复（priority 0）：site.unauthorized（未授权）· ref.stale（引用失效）· binding.stale（绑定失效）
    • 引导（priority 1）：llm.missing（LLM 未配置）· site.unbound（无活跃站点）· perm.missing（权限缺失）
    • 发现（priority 2~3）：manage.revoke（管理动作）· help.discover（看看能做什么）

    口径说明 · 法七 / 法八 的验收口径（可机核）

    法七 验收口径 —— 死端判定

    • 阻塞终态（5 类，本稿各有样例）：未授权（#msg-g-error-unauth）· LLM 未配置（#msg-g-sys-llm-missing）· 权限缺失（#msg-g-next-perm）· 绑定失效（#msg-g-error-binding）· 引用全失效（#msg-g-ref-stale）。
    • 死端判定式：阻塞终态出现后 N 秒内，流内不存在任何可达的 next → 判定为死端。本稿取最严的 N = 0（同屏紧随）。
    • 机核方式（option-g-shim.mjs §F 组）：对每个阻塞卡，取其之后最近的同场景可见兄弟节点， 断言它是 [data-msg-type="nextstep"] 且含 [data-act="next"][data-op]； 或该阻塞卡自身行内即含 [data-act="next"][data-op]（✖ 行不裸奔，本稿两处都成立）。
    • 错误行加严：[data-msg-type="error"] 卡必须满足上一条 —— 这是把真机 R3 变成回归测试的方式。

    授权态的归属（作者 2026-09-21 反馈修订：状态归状态栏，工具栏只管工具 / 导航）

    作者原话：「未授权 · 零注入」「已授权 · supported」这两项如果属于状态，那就放到最下面的状态栏，上面属于工具、菜单栏，不应该放这两个。

    • 唯一常显载体：授权态在本稿只有一个常显载体 —— 状态栏常显 chip（#auth-state）。 工具栏摘要（F 实装为 origin + 授权态）只留 origin · 会话； 四词「未授权 / 已授权 / 零注入 / supported」在工具栏区零出现（机核：§M1）。
    • 两态原文：黄态 未授权 · 零注入（页面侧未注入）· 绿态 已授权 · supported （声明 web-cli/0.2 校验通过）。两态恒显其一 —— 零风险也有，它是状态不是风险。
    • 点击行为（法七：一切操作皆 Next）：黄态点击 → 流内产出「授权当前站点」next 卡 （op.authorize · P0 恢复）+ 追加一条系统事件行；绿态点击 → 展开管理详情 （撤销授权 op.revoke / 重新绑定 op.rebind）。两种点击都不跳走、不更换面板。
    • 零双写：原风险 rail 里条件性的「未授权」chip 已并入该常显 chip；风险 rail 只承载其余风险类 （如「引用失效 ①」）。状态栏第一行只写会话 / 队列事实，不写授权态 / 协议支持 （机核：§M10 / §M12 四词扫描）。
    • 角色口径（为什么不算双写）：状态栏 chip = 「当前状态」（常显、可点、触发 next，随 ctx 变化而变）； 流内系统事件行 / 卡 = 「事实发生」（追加式留痕，只追加、不撤回，记录「何时 / 哪个 op / 成功与否」）。 前者会变、后者不变 —— 角色不同，不是同一信息的双写。
    • 台账不复制状态：L2 树视图的站点行改为指向 状态见状态栏授权 chip， 台账只做记录；状态只有一个家。

    已知取舍

    • 「恢复优先」会让流更啰嗦：每个阻塞都要求一张恢复卡。取舍是选「永远有出路」而不是「流最短」—— 用 chips ≤3 + 每回合 ≤1 张推荐卡兜住密度。
    • 注册表是运行时数据，本稿是静态单文件：视察器里的 provider 列表由内联 JS 注册表渲染（真实求值）， 但 handleCardAction 的 diff = 0 是设计性质而非运行时度量（本稿用「分发器无 per-op 分支」实现它）。
    • 掩码输入无法证伪「存储侧明文」：设计稿只能保证流内零明文；存储侧的加密与生命周期由实现负责，不在 UI 稿口径内。
    • 浏览器权限的不可逆性由浏览器决定：op.perm.request 只能申请，回收必须由用户在浏览器侧确认 —— G 把它如实说清楚，不假装能静默回收。
    • anything-is-plugin 的原文未能核实（检索凭证缺失）：引用 URL 由作者 2026-09-21 提供 （https://github.com/deepseek-ai/deepseek-harness），仓库内容未经在线核实； 落地口径以作者口述为准，已在头注与本节如实登记。
    • 连续宽度让「窄屏兜底」不再有档位边界：原三档（320 / 400 / 520）可枚举、易断言； 改为 280–640px 连续宽度后，窄屏样式（隐藏视图文字标签、压缩站点 origin）改由 #panel[data-narrow="true"]（当前宽度 ≤360px）触发。 取舍是选「贴近真实拖拽体验 + 键盘可达」而不是「可枚举的档位」。
    • 拖动性能与布局抖动：拖动只改写 :root --panel-w（单条自定义属性的宽度消费）， 连续 pointermove 经 requestAnimationFrame 合并为每帧一次写入； 面板内部换行导致的回流无法完全避免，本稿按「量力而行」处理，不作性能承诺。
    • 状态栏高度微增（授权态下移的代价，如实登记）：授权 chip 常显后状态栏多一行（约 +18px）， 换取「状态归状态栏、工具归工具栏」的单一归属与零双写。窄屏（≤360px）下工具栏摘要的「· 会话已连接」 自动隐藏，宽度预算与横向溢出都不受影响；工具栏可点数与 F 相同（5）。
    • 授权 chip 的两态由 JS 按 ctx 求值（不是 data-scenes 静态声明）：因为「授权后转绿」是同一个场景内 的状态变化（S2 断样板的核心叙事），不能靠切场景表达。取舍是选「状态可流转」而不是「纯静态可枚举」； 代价是：若脚本未执行，静态 HTML 只呈现默认态（S1 = 黄）。
    • 风险 rail 在无风险场景退化为零高容器：授权 chip 独立成行后，rail 里只剩「引用失效」一类 （S6 / S7 可见）；其余场景显示一行「无其他风险」而不是折叠掉容器 —— 保留「状态栏永不折叠」的承诺。
