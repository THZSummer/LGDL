web-cli plugin · 侧边栏布局重构 —— 三方案对比

同一份真实事实、同一组样例情境下的三种布局取向。点卡片用相对路径直接打开对应稿 （file:// 双击即可，无需服务器；三份稿都是自包含单文件）。

产品：Chrome MV3 扩展 web-cli plugin v0.8.0 · UI 面 = 侧边栏（主界面）+ 设置页 options · 侧栏宽度通常 320–560px（窄屏优先）· 深浅色跟随系统 · 三份稿均为纯设计稿：零外链 / 零 CDN / 零外部字体 / 零网络请求 / 零框架 / 零构建，不改动仓库既有文件。

无折叠抽屉，命令目录与 L1·L2·L3 三层对账常驻在同一滚动流里。 v2 新增 —— 含页面侧交互（侧栏与页面是同一个交互系统）：演示外壳改为「模拟浏览器窗口」（左 = 宿主页面，右 = 侧栏）； 意图从页面上「指」出来：右键引用（自绘菜单，零新增权限，菜单里保留「交给页面原生菜单」出口）· Alt 悬停拾取（描边 + 语义路径 / 选择器 / 文本摘要标签）· Alt + —— 把连接树当主工作面、要求每一步的后果与策略档都摊开可见、 不接受自由文本指令作为默认路径的场景。 主要取舍：D 与其他三稿哲学不同 —— A / B / C 都保留常驻输入框与对话流，D 取消常驻输入（输入只在选项内兜底）。 「信息全可见」在 320px 下换来的是「两段滚动」（连接树常驻固定 + 决策流主滚动），而不是「一屏塞下全部」：牺牲一屏可见，保住零隐藏。 打开方案 D（无输入框 · 选择题引导式）→ E 渐进式披露（随用随取） option-e-progressive.html 已交付 做法：与 D 同哲学、反密度 —— 默认低密度，按「三层披露模型」随用随取：L0 常驻只回答三件事 （我在哪 / 谁在管 / 下一步做什么：状态带 + 当前那一张决策卡 + 一行可点开的状态栏 + 一个「从页面拾取」入口）； L1 实测密度（Node 垫片对两份稿件同口径统计）：可点元素 80 → 7（−91%）· 可见正文字符 4,870 → 321（−93%）· 可见正文行数 144 → 10（−93%）· 可见文本块 391 → 47（−88%）；「全部展开」对照态 73 可点 / 121 行（≈ D 的铺开程度）。 最适合：把「少即是多」当设计目标、希望默认态一眼就懂「现在只有一件事要做」的场景；同时保留安全底线 —— 风险与状态永不折叠（未授权 / 探测中 / 硬底线被拦 / 破坏性确认 / 引用失效 五类信息必须留在 L0）。 主要取舍：与 D 并排看最直观（D = 高密度对照物）。E 推翻 D 的「无浮层 / 无折叠 / 无 ⋯ 菜单」与「树常驻」两条法则， 保留 D 的内核三条：主界面无常驻输入框（意图靠页面拾取）· 每回合一道选择题（末项固定「其他…（我来描述）」）· 页面即输入。 代价：信息不在同屏（但都有摘要 + 计数 + 明确入口，≤2 次交互可达），需要用户接受"按需取用"。 打开方案 E（渐进式披露）→ F 聊天流统一承载 option-f-chat-stream.html 已交付 一句话定位：工具栏 + 聊天流 + 状态栏三区，一切交互皆消息 —— AI 答复、用户发言、下一步推荐、 ask-user 问答、权限申请、系统事件、页面引用，7
