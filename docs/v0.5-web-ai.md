## 0. 实现演进（与早期设计的差异）

开发中协议与能力有重要演进，早期设计（§3 起）的「markdown 围栏协议块」已被**原生 function calling** 取代。以下为最终架构：

| 维度 | 早期设计（§3） | 最终实现 |
|---|---|---|
| 通讯协议 | ```` ```lgdl-web-cli ```` 围栏代码块 → 文本解析执行 | **LLM 原生 function calling**（OpenAI `tool_calls` / Claude `tool_use`），chat 文本与工具执行由 API 字段区分，工具结果以 `tool` 角色回传 |
| 工具 | 单一 lgdl-web-cli | **三平级工具**：`lgdl-web-cli`（图内容）/ `lgdl-web-op-cli`（UI 操作）/ `lgdl-web-fetch`（基础 web 获取，独立于任何 CLI） |
| 命令集 | status/validate/init/convert + 9 增量命令 | 增加**只读查询**（doc-info / get-node / get-edge / find-node / list-node-kinds / list-diagram-types，core/queries.ts 单一实现 CLI 与 Web 共享）、`init --type`（9 种模板）、UI 操作、`next-actions` 推荐胶囊 |
| 知识加载 | system prompt 内置规范摘要 | **两层知识**：方法论指南 `README-CLI.md` 由系统会话开始自动加载注入 system（战略层）；命令用法 `--help` 按需查询（战术层，自文档化，增量命令参数从 core 注册表动态生成） |
| 交互参与感 | — | AI 定位为 Web Workbench **网站操作助手**，绘图过程适合时机用 op-cli 做页面交互（preview-click/hover/reset、next-actions 胶囊），让用户看得见、保持参与感 |

### 三平级工具（最终）

| 工具 | 定位 | 子命令 |
|---|---|---|
| `lgdl-web-cli` | 图内容操作（读多写少） | status / validate / init --type / convert --to / add\|remove\|update × node/edge/group（9）/ doc-info / get-node / get-edge / find-node / list-node-kinds / list-diagram-types |
| `lgdl-web-op-cli` | UI 操作（页面交互，与手动点击等效） | copy-source / toggle-editor / collapse-editor / expand-editor / export-svg / export-png / preview-zoom / preview-pan / preview-reset / preview-click / preview-hover / switch-example / list-examples / list-diagram-types / next-actions |
| `lgdl-web-fetch` | 基础 web 获取（独立于 CLI） | `--path <path>`（必填、无默认值） |

### 两层知识（最终）

- **战略层（方法论）**：`README-CLI.md`——三个工具分工、做事流程、常见陷阱；会话开始时由系统自动 fetch 注入 system prompt（不依赖 AI 调 fetch，治模型漏传 `--path`）
- **战术层（实操）**：`--help`——具体命令用法（参数必填/可选、示例、说明）；`lgdl-web-cli <cmd> --help` / `help <cmd>` / 顶层 `--help`，`--help` 优先级最高（忽略其他校验）

### 终端 CLI 同步（clig.dev / GNU 规范）

- `lgdl-cli` 19 个命令全部提供 `--help`（含 `Examples:` 段）与 `help [command]` 子命令、无参数显示顶层帮助、错误后显示失败命令帮助
- 命令业务逻辑与 Web 共用 `core/commands.ts` 注册表（参数 schema / buildOperation / attrs/member 解析），两端只做输入适配

### 其他落地细节

- **设置面板**：服务商 + Key（各厂商独立保存）+ 模型/baseURL + maxRounds（agent 轮数上限）；不可直连厂商（火山三套餐）显示 ⚠ 警告并禁用
- **agent 循环**：每轮 1~3 次工具调用 → 执行 → tool 结果回传 → 失败反馈修正；工具枚举含 `help` 子命令（AI 查用法）
- **next-actions**：独立消息类型（胶囊卡片），点击把 prompt 作为用户指令发送

## 1. 目标与范围

在现有 Web 工作台（`packages/web`）内嵌 AI 助手，让用户通过自然语言生成新图或修改当前图，AI 输出的 LGDL 一键应用到编辑器并实时渲染。

**范围**（MVP）：

- ✅ 左栏上下分栏布局（编辑器 40% / AI 对话框 60%，分隔条可拖，编辑器可收缩）
- ✅ 对话生成新图 / 修改当前图（当前源码自动注入上下文）
- ✅ 输出 LGDL 代码块 → 「应用」按钮 → 写入编辑器 → 实时渲染
- ✅ 多厂商 API 接入（DeepSeek / Qwen / 火山方舟 / 腾讯混元 / GPT / Claude），用户手动填 key，系统不内置 key
- ❌ 图解释 / 评审 / 选区操作（后续版本）
- ❌ 图即代码（语义 diff、CI 渲染、set-type 等）——推到 v0.6

## 2. 布局改造

当前 `.workspace` 为左右两栏（左编辑器 / 右预览）。改为：

```
+--------------------------------------------+
| header（品牌 + 示例切换器）                 |
+----------------------+---------------------+
| 编辑器 pane（上部 40%）|                     |
| +------------------+ |  预览 pane（不变）    |
| | 分隔条（可拖动）   | |                     |
| +------------------+ |                     |
| AI 对话框（下部 60%）| |                     |
|                     | |                     |
+----------------------+---------------------+
```

- 左栏垂直分割：编辑器（默认 40%）+ AI 对话框（默认 60%），中间分隔条可自由拖动调整比例
- 编辑器可收缩：分隔条拖到最底部自动收起（编辑器折叠为标题栏），点标题栏重新展开
- 右侧预览 pane 布局完全不变
- 实现：flex 布局 + 分隔条 pointer 拖拽，编辑器高度由 `flex-basis` 控制；收缩状态用 state 记录，拖动与收缩互斥（拖拽中不触发收缩，松手后才判定）

## 3. 对话能力（MVP）

### 3.1 交互（命令模式 —— AI 不直接写源码）

- AI 对话框位于左栏下部：消息列表（用户/AI）+ 输入框
- 用户输入自然语言 → 发送 → AI 返回 Markdown（含 **```lgdl-web-cli 命令块**）
- AI 像在 Linux 终端里一样用 `lgdl` 命令操作图（`lgdl-cli status` / `lgdl-cli add-node --id x --label y` …），**不直接输出 LGDL 源码**——源码只能由命令执行产生
- AI 回复中的命令块右上角有「执行」按钮：
  - 逐条解析（`web/ai/web-cli.ts` + `core/commands.ts`，与 lgdl-cli 同语义）→ `applyOperations` 应用到当前编辑器源码 → `validate` 门禁 → 写入编辑器实时渲染
  - status 命令输出当前图结构文本（`formatStatus`），供 AI 与用户理解图
  - 任一条失败即停，红框展示失败原因（失败即停与 CLI 一致）

### 3.2 上下文注入

每次请求自动拼接 system prompt + 当前图上下文：

```
system: LGDL 命令规范（可用命令、参数、使用流程、硬性约束）
user:   [当前源码]（若编辑器非空，供 AI 理解图；AI 不得输出源码）
        用户指令：<自然语言>
```

- 当前源码从编辑器读取（`source` state），注入供 AI 理解，但 system prompt 明确禁止 AI 输出源码块（只允许 ```bash 命令块）
- 生成新图：AI 先 `lgdl-cli status`（空图提示）再逐条 add-node / add-edge 搭建
- 修改当前图：AI 先 `lgdl-cli status` 读图，再增量命令修改

### 3.3 校验门禁（validate 门禁）

命令执行后必须通过：

1. 每条命令解析失败即停（`parseCommandBatch`）
2. `applyOperations` 执行失败即停，返回已执行部分
3. 结果 `validate()` 通过后序列化写入编辑器，现有 linter/渲染链路自动工作
4. 失败：红框展示失败命令 + 原因，提示用户修正或让 AI 重试

### 3.4 双 CLI 分离 + 命令业务逻辑复用

**lgdl-cli 与 lgdl-web-cli 物理分离、场景独立，业务逻辑单一实现**：

| | lgdl-cli（终端） | lgdl-web-cli（Web 协议） |
|---|---|---|
| 位置 | `packages/cli` | `packages/web/src/ai/web-cli.ts` |
| 输入适配 | commander（argv） | 文本解析（协议块） |
| 对象参数 | `--file <path>`（磁盘文件） | `--doc <id>`（编辑器文档） |
| 命令业务逻辑 | 共用 `core/commands.ts` | 共用 `core/commands.ts` |

- `core/commands.ts` 是**命令业务逻辑唯一实现**：`COMMANDS` 注册表（参数 schema / 必填 / no-change 键）、`buildOperation`（统一 op 构造，含 add-node 按图类型默认 kind）、`parseAttrsSpec` / `parseMemberSpec`
- 两端只做「输入适配」，参数校验、op 构造、attrs/member 解析、错误信息完全一致

### 3.5 lgdl-web-cli 通讯协议（表达 vs 执行）

AI 与工作台之间定义**标准协议**，明确区分"说话"与"执行"：

| 载体 | 语义 | 是否执行 |
|---|---|---|
| 普通文本 | chat 表达（解释/计划/总结） | ❌ 不解析不执行 |
| ```` ```lgdl-web-cli ```` 代码块 | **lgdl-web-cli 执行调用**（每行一个 `lgdl <子命令> --doc <id> --key value`） | ✅ 解析并逐条执行 |
| 其他代码块（bash/code/yaml…） | 视为普通文本 | ❌ |

- **`--doc <id>` 是 lgdl-web-cli 必填参数**（操作对象标识，对应 lgdl-cli 的 `--file`）；当前文档 id 为 `main`
- AI 不直接写 LGDL 源码——源码只能由 `lgdl-web-cli` 调用执行产生
- 执行结果（status 输出 / ✓ 摘要 / ✖ 错误）以 **tool 消息**（终端样式）反馈回对话，并作为下一轮 LLM 上下文（映射为 user 角色 + `[web-cli 执行结果]` 前缀）
- **agent 循环**：每轮 AI 输出 1~3 条调用 → 执行 → 结果反馈 → AI 继续，直到总结收尾或达到 10 轮上限；失败会反馈给 AI 让其修正（终端体验）
- 协议实现在 `web/ops.ts`（`extractCommands` 只认 lgdl-web-cli 围栏）+ `web/ai/web-cli.ts`（解析，复用 `core/commands.ts`）+ `applyOperations`（执行）

### 3.6 命令集（lgdl-web-cli）

| 命令 | 作用 |
|---|---|
| `status` | 查看当前文档图结构 |
| `validate` | 校验当前文档语法（错误/警告） |
| `init` | 清空文档为默认图 |
| `convert --to mermaid\|plantuml\|json` | 导出为其他格式（不改动文档） |
| `add-node` / `remove-node` / `update-node` | 节点增删改 |
| `add-edge` / `remove-edge` / `update-edge` | 边增删改 |
| `add-group` / `remove-group` / `update-group` | 分组增删改 |

render 由编辑器实时渲染等价实现（无需命令）；import 依赖多文档能力，v0.6 评估。

## 4. Provider 层（多厂商 API）

### 4.1 原则

- **系统不内置任何 apiKey**，只允许用户手动输入
- key 存 `localStorage`（仅本地使用，不上传）
- 默认支持常见厂商，可扩展

### 4.2 厂商接入

| 厂商 | baseURL | 适配 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com` | openai SDK |
| Qwen（阿里百炼） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | openai SDK |
| 火山方舟 Ark | `https://ark.cn-beijing.volces.com/api/v3` | openai SDK |
| 腾讯混元 | `https://api.hunyuan.cloud.tencent.com/v1` | openai SDK |
| GPT (OpenAI) | `https://api.openai.com/v1` | openai SDK |
| Claude (Anthropic) | 原生 Messages API | `@anthropic-ai/sdk` |

- 统一抽象：`ProviderConfig { id, name, baseURL, apiKey, model }`
- openai SDK 浏览器直连需 `dangerouslyAllowBrowser: true`（官方支持）
- Claude 单独分支走 `@anthropic-ai/sdk`
- 厂商列表可在设置面板选择；model 默认值按厂商预填（如 deepseek-chat / qwen-plus / doubao-… / hunyuan-… / gpt-4o-mini / claude-3-5-haiku），允许用户覆盖

### 4.3 错误处理

- CORS 失败 / 网络错误 / 401（key 无效）→ 明确的错误提示，区分「key 无效」「网络不通」「厂商 CORS 不允许」三种情况
- 请求超时 / 输出为空 → 提示重试
- 流式输出（SSE）：MVP 先做**非流式**（完整返回），流式列入后续优化

### 4.4 CORS 实测结论（2026-08-23）

浏览器直连依赖厂商 CORS 预检允许认证头。实测：

| 厂商 | 预检结果 | 浏览器直连 |
|---|---|---|
| DeepSeek | 允许 `authorization,content-type` | ✅ |
| Qwen（阿里百炼） | 允许 `authorization,content-type` | ✅ |
| 腾讯混元 | 返回 allow-origin + allow-headers | ✅ |
| OpenAI / Anthropic | 官方 SDK 支持浏览器 | ✅ |
| 火山方舟（通用/Coding/Plan） | 仅 `Origin,Content-Length,Content-Type`，认证头被拦 | ❌ |

- 配置面板对不可直连厂商（火山三个套餐）显示 ⚠ 警告并禁用测试/发送
- 「测试连接」按钮：配置时发最小请求验证 key/端点/CORS
- 火山等受限厂商需本地代理（`lgdl-cli serve`）——列入 v0.6

## 6. 风险与验证

- **CORS**：OpenAI 官方支持浏览器直连；DeepSeek 实际可直连；火山/腾讯需实现时实测，不通则给出明确报错（符合「有损必警告」）
- **输出质量**：AI 生成 LGDL 依赖规范提示词质量，用现有示例（EXAMPLES）做回归验证——生成结果必须通过 `validate()` 且渲染不报错
- **key 安全**：只存 localStorage、不上传、不写日志；README 明确说明风险由用户自担
