### 0.3 实测密度证据（**同口径实测，非估算**）

来源：`design/ui-redesign/index.html`「D 与 E 默认态的密度实测对照」（Node 垫片对两份稿件同口径统计）。口径：可点元素 = 面板内**非 `hidden` 子树**中的 `button/a/input/select/textarea` + `tabindex≠-1` 元素；可见正文字符 = 上述元素自身直接文本去空白之和（每段只计一次）；可见文本块 = 自身直接文本非空的可见元素个数；常驻分区数 = 面板一级子元素中非 `hidden` 的个数。

| 默认首屏指标 | D（无输入框选择题） | E（渐进式披露·L0） | 降幅 | E「全部展开」对照态 |
|---|---:|---:|---:|---:|
| 可点元素数 | 80 | **7** | −91% | 73 |
| 可见正文字符数 | 4,870 | **321** | −93% | 4,089 |
| 可见正文行数（≈字符 ÷ 34） | ≈144 | **≈10** | −93% | 121 |
| 可见文本块数 | 391 | **47** | −88% | 347 |
| 面板常驻分区数 | 5 | **6** | **+1** | 7 |

> 两条**必须一并记录的反直觉事实**（防止后续阶段把 E 简化成「删东西」）：
> 1. **常驻分区数 E 反而 +1**（5 → 6）——E 把顶部分成「状态带」与「**风险位**」两块，让风险**独立常驻**。分区更细 ≠ 信息更多：E 的可点元素只有 D 的 1/11。
> 2. **E「全部展开」态刻意复现 D 的铺开程度**（73 可点 / 121 行）——用来证明**密度差来自披露策略而非功能缺失**：两态能力集完全相同（同一批命令、同一批档位、同一棵四维树、同一份 122 卡目录、同一份审计）。

## 1. 问题定义

> 概括核心问题及其业务影响，回答"为什么需要关注"

### 1.1 一句话问题陈述

**已绑定并授权站点的 web-cli-plugin 日常使用者（首位真实用户即作者本人），在打开侧栏、想「在当前站点上完成一件事」的这一场景下，面对的是一个把状态、会话、连接树、命令目录、技术确认、自由输入、设置等 5+ 类信息同时平铺在同一默认首屏的界面（实测 80 个可点元素、4,870 个可见正文字符 ≈144 行、391 个文本块、54 个 DOM `id`），因而无法回答「我现在只需要做哪一件事」——他必须自己在满屏信息里做筛选和降噪；代价是作者真机给出「凌乱、没有条理 / 很复杂、很难用、信息密度太高」的判断，学习成本与误操作风险（尤其授权类、破坏性确认类高后果操作与普通信息同密度并列）被同时抬高，而 v2 刚加入的连接树与命令档案只会让同一屏继续变挤（越做越难用），进而动摇「插件替代内置 AI 助手」这一立项命题的可信度。**

### 1.2 核心问题与业务影响

| 核心问题 | 业务影响 | 不解决的成本 |
|---------|---------|------------|
| **默认首屏信息密度压倒一切**：所有类别的信息默认同屏铺开，用户无法一眼识别「当前唯一要做的一件事」 | 插件作为「独立于 LGDL、可作用于任意声明 web-cli 站点」的通用消费端，第一印象是「复杂难用」；体验门槛直接抵消 v1/v2 交付的能力价值 | 作者真机判断已给出（「很难用」）；能力越全越难用，产品可信度与推广意愿持续下降 |
| **信息缺乏稳定层级与归属**（作者原话「凌乱，没有条理」）：54 个 `id` 的主要分区平铺在同一条滚动流里，没有「我在哪 / 谁在管我 / 下一步做什么」的固定骨架 | 用户无法建立稳定的空间心智模型；每次使用都要重新定位 | 每次交互都要额外认知开销；错误操作概率上升；新用户（生态用户）更易放弃 |
| **风险与状态信息被淹没**：未授权 / 探测中 / 硬底线被拦 / 破坏性待确认 / 引用失效 五类高后果信息与普通信息同密度并列，没有「永不折叠」的常驻位 | 安全面「可见即可控」的既有原则被密度稀释：**信息存在但看不到等于不存在** | 用户可能在未察觉「未授权 / 硬底线被拦」的状态下继续操作；破坏性确认可能被当成普通卡片误触或误忽略 |
| **能力增长与侧栏容量的结构性矛盾**：v2 已把四维连接树 / 122 卡命令档案 / 撤销回执压进同一屏，v3 还要再加页面侧拾取层 | 每个新能力都在同一个默认首屏上加码 → 能力增长路径与可用性路径**方向相反** | 后续任何能力迭代都会继续恶化作者已反馈的问题；形成「不敢加功能」的长期天花板 |

## 2. 用户画像

> 描述受影响用户角色及其场景，回答"谁遇到了什么问题"

| 用户角色 | 典型场景 | 关键痛点（用户原话） | 当前应对方式 |
|---------|---------|-------------------|------------|
| **日常站点使用者（首位真实用户 = 作者本人，也是当前唯一用户）** | 在已授权站点（如 LGDL Web 工作台）打开侧栏，想「让插件在这页上做一件事」 | 「web-cli-plugin 的整个 UI 布局还是比较凌乱，没有条理」；「让人感觉你这个系统很复杂、很难用，信息密度太高了」 | **忍受**：继续使用但每次自行在满屏信息里筛选；同时提出「随用随取 / 渐进式披露」的诉求（= 明确表达期望的理想状态） |
| 窄侧栏使用者（320–560px，窄屏优先） | 侧栏拖窄到 320px 仍要完成同一批任务 | 无原话；事实约束 = 现有 320px 门禁只保证「零水平溢出」，不保证「信息可读 / 可发现」 | 忍受纵向滚动（推断，🟠 待验证） |
| 新用户 / 生态用户（后续 web-cli 站点用户） | 首次安装：先遇 onboarding + discovery-notice + 空态，再遇满屏功能 | 无原话（作者本人已过首装期）；痛点与首行者同源但更重 | 放弃（推断，🟠 待验证；见 A-UI-009） |
| 维护者 / 开发者（AI Agent + 作者） | 每次 UI 改动都要跑门禁 | 无原话；事实约束 = Chromium 门禁的运行时断言与静态 DOM 契约**直接钉住当前 DOM**，UI 重设计的变更成本高 | 走「断言取代台账」（既有先例：`docs/r2-supersession-ledger.json`） |

**用户旅程（现状，痛点位置标注）**:

```
[安装] → onboarding / discovery-notice（首屏即两层技术说明）
   ↓
[绑定 + 授权] → 侧栏同时出现：状态条 + LLM 徽标 + 会话盒 + 站点提示 + 环境守卫
   ↓  ← ★痛点 1：还不知道能做什么，先被告知一堆「能不能用」
[想做事] → 需要自己判断：先探测？先看树？先看命令？还是先打字？
   ↓  ← ★痛点 2：没有「下一步做什么」的单一指引；54 个 id 平铺
[表达意图] → 唯一通道 = composer 打字（页面上的目标只能"描述"，不能"指"）
   ↓  ← ★痛点 3：指代成本高（Q-UI-005）
[执行 / 确认] → 技术确认卡 + 破坏性确认 + 回执 与普通消息同流同密度
   ↓  ← ★痛点 4：高后果信息不显眼（Q-UI-003）
[想查全貌] → 树抽屉 / 命令档案 / 审计 / 设置 都是「覆盖式」打开，查完要回位
```

**关键转折点**：上述 ★痛点 2（不知道下一步做什么）——它是作者「凌乱、没有条理」反馈的直接对应物，也是「渐进式披露」诉求要解决的核心；★痛点 1 与 ★痛点 4 共同决定「哪些信息不能藏」（对应 D3 风险位常驻）。

| **Q-UI-005** | **意图表达通道单一：只能打字，用户看着页面上的对象却无法「指」给它。** 现状唯一输入通道是 `#composer`（输入框 + 发送）；用户在页面上看到目标（某个卡片、某行、某段文本）时，只能**用语言描述**它，指代成本高、易说错目标。 | 每次需要针对页面具体对象的操作；对应 D4③「页面即输入」的缺失面 |

### 3.3 潜在问题

> 目前影响小但可能恶化，或信息不足待验证

| ID | 问题描述 | 影响范围 |
|----|---------|---------|
| **Q-UI-009** | **`content.js` 体积余量为 0，与「新增页面侧交互层」正面冲突。** `dist/content.js` 实测 **177,076 B**，`CONTENT_MAX_BYTES` 也是 **177,076 B**（无容差，+1B 即 FAIL）。而 Alt 悬停拾取 / 拖动入侧栏 / 右键自绘菜单 / 拖选气泡 / 双向联动全部属于**页面侧代码**，天然落在 `content.js` 内。 | 决定 D4③「页面即输入」是否可行；是本 Feature 的头号技术风险（见 R-UI-001） |
| **Q-UI-010** | **收起/展开一旦不是「真隐藏」，无障碍与双主题就会退化为视觉技巧。** 渐进式披露会引入大量展开/收起状态；若不用 `aria-expanded` / `aria-controls` 与 `hidden`（而非 CSS 视觉隐藏），键盘与读屏用户将无法到达被收起的内容；明暗双主题下若只靠颜色表达状态（如风险等级、策略档位）也会失效。 | 无障碍用户；明暗双主题（跟随系统） |
| **Q-UI-011** | **「引用失效」语义未定义。** 页面拾取产生的引用天然会因页面导航、DOM 变更、元素卸载而失效。现状无任何「引用」概念，因此也无「失效」判定与提示。若失效引用被静默沿用，用户可能对着一个已不存在（或已变成另一个对象）的目标下指令。 | 页面即输入路径（Q-UI-005/006 的解决路径）；D3 已把「引用失效」列入必须常驻的五类风险信息，但**判定语义仍缺** |
| **Q-UI-012** | **页面侧 UI 与「未授权站点零注入」授权哲学的边界未验证。** 现架构为零静态 `content_scripts` + 绑定后按 origin 登记注入（`registerContentScripts` 对无 host permission 的 origin 直接失败）。页面侧新增拾取层/右键菜单必须维持该性质；一旦实现走偏（如为省事申请全站 host permission 或静态注入），将破坏既有零注入红线。 | 安全/合规面；与 Q-UI-006 的解决路径直接耦合 |

### 5.2 主要风险

| # | 风险描述 | 影响程度 |
|---|---------|---------|
| **R-UI-001** | **`content.js` 体积上限 vs 页面侧交互层（头号风险）。** 实测 `dist/content.js` = **177,076 B**，上限也是 **177,076 B**，**余量 0 字节、无容差**。而页面即输入的四项交互（Alt 悬停拾取 / Alt 拖动入侧栏 / 右键自绘菜单 / 拖选文本气泡）本质都是页面侧代码；此外 `src/content/**` 三个文件还有**内容哈希冻结**（`CONTENT_SOURCE_SHA256`：`content-script.ts` / `dom-agent.ts` / `page-bridge.ts`），任何字节改动（含空白）都会 FAIL，须显式更新 pin 并注明日期与理由。 | 🔴 **高** |
| **R-UI-002** | **既有 UI 断言被打破的取代路径（第二个高风险）。** `test:ui` journey 167 / insight 108、`test:binding` 192 运行时断言 + `sidepanel-view.test.ts` 静态 DOM/CSS 契约（含 4 项布局类）均直接钉住当前 DOM（实测 `querySelector`/`getElementById` 引用：journey 32/134、insight 118/42、binding 25/63）。纪律为**零删除、零降级**。 | 🔴 **高** |
| **R-UI-003** | **320px 与信息密度的张力。** 既有门禁只保证零水平溢出；而「一屏塞下全部」在 320px 下数学上不成立（E 稿自身承认代价：需要用户接受按需取用；D 稿在 320px 下是"两段滚动"）。若 spec 阶段出现「既要常驻全部风险位、又不许滚动」类要求，将不可实现。 | 🔴 **高** |
| **R-UI-004** | **`contextMenus` 权限缺失（已定论走路线 1，但需三条退让兜底）。** manifest 静态权限不含 `contextMenus`，也未列入 optional → **不可能**使用平台右键菜单 API；只能 content script 自绘（零新增权限），并承担三条退让：仅已授权站点生效 / 保留「交给页面原生菜单」出口 / `Esc` 与点击空白即关。自绘菜单天然可能被宿主页面样式/CSS 干扰（shadow DOM 或高 z-index 需求），且无法获得平台级「其它扩展菜单项」语义。 | 🟡 **中高** |
| **R-UI-005** | **设计稿 ≠ 真实产物。** 五份稿均为自包含单文件（零外链/零 CDN/零构建/不改仓库既有文件），是**模拟环境**（含"模拟浏览器窗口"外壳）；其密度数字、状态机演示与真实 MV3 侧栏（CSP、`storage`、SW 通信、真实 origin 探测）之间必然有落差。 | 🟡 中 |
| **R-UI-006** | **安全判定链被 UI 化改动波及。** 红线：判定链 sha256 pin（`policy.ts` `bfcb2ede…` / `auto-authorize.ts` `1096d065…`）不得改动；硬底线（`evaluate` / 未授权 origin / 未知 risk）不可覆盖；`ui/state/external` 只可收紧（无 allow）；`dom` 三档可用；破坏性子命令**保底 ask**；clamp 在 **SW 侧强制**（UI 只提示，伪造 `sendMessage` 不能突破）；树内动作白名单 **9 个（固定序）**。UI 层新增任何「策略/后果/风险徽标」展示都属于**只读投影**，一旦变成可写入口即破红线。 | 🔴 **高** |
| **R-UI-007** | **可发现性回归。** 「渐进式披露」的最大失败模式是变成「藏起来找不到」。已定论硬约束为：凡收起必须有**摘要/计数 + 入口**，禁止无线索隐藏；L1 = ≤1 次交互、L2 = ≤2 次交互可达。若实施中为压密度而省略计数或入口，将整体退回给作者一个更差的界面。 | 🟡 中 |
| **R-UI-008** | **零注入红线被破坏。** 页面侧 UI 只在**已授权站点**存在（登记式零注入：绑定后才注册 content script，未授权站点零注入、不注册监听、不渲染拾取 UI、不拦截右键）。若为降低实现复杂度而改为静态注入或扩大 host permission 范围，即破红线且与 `manifest.json` 现状不符。 | 🔴 **高** |
| **R-UI-009** | **无障碍与明暗双主题遗漏。** 需 `aria-expanded` / `aria-controls`（收起用 `hidden` 而非视觉隐藏）、`:focus-visible`、数字键选择、不靠颜色单独传达状态。披露层数量增多会显著放大遗漏面。 | 🟡 中 |

| **R-UI-011** | **「引用失效」语义未定义 → 带失效引用继续操作。** 引用失效已被列为必须常驻的五类风险信息之一（D3），但其**判定条件**（元素消失 / origin 变更 / 页面导航 / 声明版本变化）与**呈现方式**均未定义；若静默沿用失效引用，用户可能对错误目标下指令。 | 🟡 中 |
| **R-UI-012** | **本机资源限制验证节奏。** 本机内存紧张（约 1.5GB，曾 OOM），Chromium 门禁（e2e / test:ui / test:insight / test:binding）必须**串行**执行、日志完整落盘；发现阶段已按纪律**不执行**任何 Chromium 门禁。 | 🟡 中 |
| **R-UI-013** | **版本位事实冲突（🟠 待拍板）。** ROADMAP 当前 `v0.9.0` 已被登记为「工程质量与文档对齐」（由原 v0.7→v0.8→v0.9 两次后移而来），而编排器对本 Feature 的建议产品版本也是 `v0.9.0`。两者目前并存，尚未见 ROADMAP 有对应登记或重排说明（`grep "specs-tree-web-cli-plugin-v3" ROADMAP.md` = 0 命中）。 | 🟡 中 |
| **R-UI-014** | **设计依据存在丢失风险。** `packages/web-cli-plugin/design/` 为 **untracked**（`git status --short` 显示 `?? packages/web-cli-plugin/design/`），且本轮明确「不动、不 commit」。E 稿作为设计基准、D 稿作为高密度参照物，若长期不入版本库，基准资产可能丢失。 | 🟡 中（低技术风险、高追溯风险） |

### 7.3 Feature 分解建议（**初步结论，供 spec/plan 收敛；discovery 只提建议不执行**）

> 编排器给定的建议（**保留，仅作评估对象**）：父 Feature + 4 叶子 = `v3-1 L0 骨架与密度门禁` · `v3-2 L1 就地展开与引用/回执` · `v3-3 L2 按需视图（树/命令/审计/设置）` · `v3-4 页面即输入（拾取层按需注入 + 右键自绘菜单 + 双向联动）`。

**discovery 复核结论：建议接受该分解（不改动），理由如下（并对编排器的自我约束做两点补充）：**

| 叶子 | 承载问题 | 为何可独立「全门禁绿」 | 复核意见 |
|------|---------|---------------------|---------|
| **v3-1 L0 骨架与密度门禁** | Q-UI-001 / 002 / 003 / 004（主干） | 先立骨架与常驻/收起契约，其余叶子都在其上叠加 → 首个叶子即可把「密度门禁」变成可测基线 | ✅ 接受。**补充 1**：建议本叶子同时产出「L0 密度口径的机器可测断言」（对照 A-UI-001，避免设计稿数字直接当验收值），否则后续叶子无共同基线 |
| **v3-2 L1 就地展开与引用/回执** | Q-UI-003（就地解释层）/ Q-UI-011（引用失效提示位） | 纯 L0→L1 的就地展开，不触碰 L2 视图与页面侧 | ✅ 接受。**补充 2**：Q-UI-011 的「引用失效」判定语义未定（R-UI-011），若本叶子要承载其**呈现**，判定语义须在 spec 阶段先定，否则会漂到 v3-4 |
| **v3-3 L2 按需视图（树/命令/审计/设置）** | Q-UI-002 / Q-UI-004 | 复用既有 `tree-drawer` / 命令档案 / 审计 / 设置资产，主要工作是「改归属方式 + 加摘要/计数/入口」 | ✅ 接受。**风险提示**：本叶子是 R-UI-002（断言取代）的最大战场——既有 insight 108 / binding 192 断言大量落在树/回执/确认上 |
| **v3-4 页面即输入（拾取层按需注入 + 右键自绘菜单 + 双向联动）** | Q-UI-005 / 006 / 007（部分）/ 009 / 012 | 与 L0/L1/L2 解耦（页面侧 vs 侧栏侧），且是唯一触碰 `content.js` 的叶子 | ✅ 接受。**风险提示**：R-UI-001 / R-UI-004 / R-UI-008 三条风险全部集中在此叶子 → 建议它是**最后一个**开工的叶子（前置 spike 通过后再动），并且**不得**用「放宽体积上限」换取功能 |

**父 Feature 定位（复核）**：父 = 轻量规范容器（聚合 spec/plan 与 review/validate 汇总报告），**不承接 tasks/build/review/validate 类阶段操作** —— 与 v2 先例一致（v2 父保持 `phase=tasked` / `workflow=4.tasks` / `agent=sddu-tasks`，仅承载聚合报告）。✅ 接受。

**未采纳的调整提议（已评估并放弃，供 spec 阶段参考）**：
- 曾考虑把「密度门禁」独立成第 5 个叶子（纯粹的可测目标）；放弃理由 = 密度口径依赖 L0 骨架存在（v3-1 的产物），独立成叶子会产生对 v3-1 的强依赖而无法独立全绿，违反编排器约束。
