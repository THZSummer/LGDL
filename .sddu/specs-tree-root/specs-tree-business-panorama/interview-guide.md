# 访谈提纲（Why 层）— LGDL 业务全景

> 受访人: 项目唯一作者兼决策者 → 可直接问决策动机、当时的候选方案、放弃原因。
> 提问原则: 不让用户复述 CHANGELOG 已有的 What；每问聚焦"为什么这么决策、当时怎么权衡、放弃了什么"。
> 锚点均来自 facts-baseline.md；答案回填本 Feature 的 discovery 产物。

## G1 问题定义与产品定位（核心痛点）
锚点: README.md:5 "彻底告别「AI 来回调整图形布局」的低效循环"；design.md:12
1. "布局拉扯循环"在你的真实经历里是什么样的？还原一次最促使你动手的具体场景：哪张图、用哪个 AI、反复拉扯了几轮、坏在哪？
2. 为什么是当时动手造 LGDL，而不是继续忍受或换现有工具？压垮决策、让你觉得"必须自己做"的那一下是什么？
3. "语义优先"在立项时是什么含义？它是从痛点直接推出来的，还是先有"AI 只该改逻辑"的直觉、再反推出这套表述？
4. 为什么定位"面向 AI Agent"，而不是"面向人、顺带 AI 友好"？当初有没有摇摆过（比如先做人类开发者工具）？
5. 如果一直不解决这个痛点，你判断会发生什么（对 AI 画图的可用性、对你自己的工作流）？

## G2 竞争定位（vs Mermaid / PlantUML / Graphviz / D2）
锚点: 存量文档无直接对比陈述（facts-baseline §3.4），只有 convert/import 互操作
1. Mermaid 离你最近（Web 生态成熟、AI 训练语料最多），为什么选择"新造一门语言"而不是基于 Mermaid 改造或做它的预处理器？
2. PlantUML/Graphviz 是"语义与布局分离"的几十年前辈，LGDL 从它们身上继承了什么、刻意反叛了什么？
3. D2 主打现代声明式与好看，你评估过它吗？从"AI 消费"视角看它差在哪？
4. "严格校验不留兼容包袱"与"AI 语料里全是 Mermaid 语法"存在迁移成本矛盾，当时怎么权衡？`import --from mermaid` 是作为这个矛盾的答案设计的吗？
5. 你希望用户依据什么判断标准"从 Mermaid 换到 LGDL"？换与不换的分界线是什么？
6. 有没有你认真考虑过、但别人很少拿来对比的方案（例如直接让 AI 写 Graphviz DOT）？

## G3 目标用户与核心场景
锚点: design.md:73 "消费方是 CLI 操作的 AI"；README.md:90 "AI 不直接写源码"；docs/v0.5-web-ai.md:16 "让用户看得见、保持参与感"
1. 你心里最典型的用户画面是什么？是你自己（开发者 + AI 协作），还是想象中更广的人群（文档工程师/产品经理/团队）？
2. 终端 CLI（lgdl-cli --file）与 Web 工作台（lgdl-web-cli --doc）分别对应你想象中的哪类场景？为什么两头都做？
3. "AI 不直接写源码、只能走命令"是很强的约束——它防的是什么具体坏结果？有没有 AI 直写源码翻车的真实实例？
4. op-cli 的"让用户看得见、保持参与感"是很产品化的判断——它从哪来？人机协作里"可见性"为什么重要到要专门做一套 UI 操作工具？
5. v0.6 "图即代码"（语义 diff/评审、CI 自动渲染）面向的是团队协作场景吗？它与"AI Agent 个人助手"场景是什么关系？
6. 9 种图类型是怎么圈定的？哪些是"AI 高频需要"，哪些只是为了补齐完整性？

## G4 语言设计的产品哲学
锚点: design.md:73；CHANGELOG.md:147/156 两条"破坏性：旧写法不再兼容"；README.md:72 "无警告级静默降级"
1. label 内 \n 拼成员、label 混基数这些旧写法，兼容成本其实很低（正则解析而已），为什么选择"校验拒绝、不留兼容包袱"而不是"宽进严出"？
2. 破坏性变更发生在已发布 npm 的 v0.4——当时怎么评估对早期用户的伤害？"不留包袱"的底气来自哪里（用户量为零？AI 重新生成成本低？）？
3. 为什么"报 error 不警告"贯彻得如此彻底？警告 + 自动修复不是对 AI 更友好吗？
4. "零猜测"的边界在哪：渲染器里有没有你曾犹豫过"要不要猜一下"的地方（如图类型默认形状、缺省方向）？
5. 语法为什么是 YAML 风格缩进 DSL，而不是 JSON（AI 生成更稳、有 schema）或完全自定义语法？有没有考虑过 token 成本？
6. "消费方是 AI 不是人"这条原则有没有被打破的时候（examples/ 画廊、README 语法速览其实都是给人看的）？

## G5 版本演进叙事
锚点: facts-baseline §1 时间线（v0.1–v0.3 同日、v0.4–v0.5 同日）、§2 三转折点
1. v0.1–v0.3 三个版本同一天发布——当天真实的开发节奏是什么？版本号切分是当时的里程碑，还是事后追认？
2. 能力主线全在 CLI/core、Web 后行——为什么这样排序？如果反过来先做 Web 会怎样？
3. v0.4 的"显性化 + 去兼容"与 v0.5 的"AI 助手"同日完成——它们是同一条决策链的产物吗（显性化是在为 AI 助手铺路）？
4. v0.5 为什么把 AI 助手做在 Web 端，而不是 CLI 端（如终端里直接接 LLM）？Web 工作台在整个 AI 故事里的角色是什么？
5. v0.6 一个版本内连迁两次布局引擎（dagre→elkjs→自研）：是什么让你从"可配置回退"走到"彻底删掉"？驱动是质量（长边绕大圈）、工程（依赖/打包 1.6MB wasm）、还是掌控力？
6. AI 实战评审闭环（pi 画 9 种图 + 视觉模型评审）出现在 v0.6——为什么现在才做系统性的"AI 当用户"验证？它改变了你对产品方向的哪些判断？
7. 回望 v0.1：哪个决策今天看依然是对的？哪个今天会做得很不一样？
