# ADR-V55-010: 并发仲裁（有界队列 1 + 明确告知 + 草稿恢复）与 SW / panel 分工

## 状态
ACCEPTED

## 背景

现状（R3 / C5 / X-SELF-7）：`chatBusy` 单飞（`service-worker.ts:879-885`）—— 并发第二条**被丢弃**并回错误
（逐字「上一条消息仍在处理中，请稍候再发送。」）；而 v5.5 一旦让 AI 也能发起回合，**撞车成为常态**：
AI 主动回合 ∥ 用户手输 ⇒ **用户输入可能被静默丢弃**（US-SELF-009 / EC-SELF-013 的母缺陷）。

spec FR-SELF-061 / 096 / 106 / AC-SELF-014 与 §8 留给 plan 的项① 要求：策略三者之一（排队 / 合并 / 明确拒绝并保留用户输入），
但必须满足 ① **用户输入永不静默丢失** ② 仲裁结果**留痕可判** ③ 仲裁**有界**；且**单飞语义本身保留**（同一时刻一个在飞回合）。

## 决策

### 1. 策略：**有界排队（1）+ 溢出即明确拒绝 + 草稿恢复**（**不选**「合并」）

| 候选 | 裁决 | 理由 |
|---|---|---|
| **合并**（把 AI 主动的指令与用户输入拼成一条回合） | **否决** | 会让 AI 的指令与用户的意图混进同一回合 ⇒ 归因不可判（谁发起 / 依据什么），且「用户的话」可能被 AI 的话稀释 |
| **无界排队** | **否决** | 违「有界」；且在飞回合可能很长 ⇒ 队列膨胀 + 用户失去即时反馈 |
| **有界排队（1）+ 明确拒绝 + 草稿回填** | **采纳** | 只用一条入口规则覆盖两种来向；溢出时**明确告知 + 输入仍属于用户**（草稿回填）⇒「永不静默丢失」在**最坏情况**下也成立 |

### 2. 用户输入路径（**永不静默丢失**，最坏情况也成立）

```
面板 requestTurn(text)（既有唯一入口，签名不变）
  → dispatch({type:'user'})（既有，流内立即可见用户这一句）
  → send('chat', {user: text})（既有）
SW runChat(user):
  ① chatBusy === false ⇒ 正常执行（既有）
  ② chatBusy === true  ∧ 队列长度 < 1 ⇒ 入队（FIFO，**硬上限 1**）→ 回 { variant:'queued' }
       面板：写系统行「已排队：上一条回合结束后自动发送」（留痕）；草稿可清（文本已在队列中）
  ③ chatBusy === true  ∧ 队列已满 ⇒ **明确拒绝** → 回 { variant:'busy-rejected', text }
       面板：写系统行「正在处理上一条，未发送（草稿已保留）」+ ★**把 text 回填到 `#input`**
  在飞回合结束（既有 finally）⇒ drain 队列（若有）⇒ 执行被排队的那一条（**同 sessionId 语义**）
```

| 判据 | 反证 |
|---|---|
| ②「已排队」留痕存在（可读行） | 去掉行 ⇒ FAIL |
| ③ 拒绝后 `#input.value === 被拒文本` **且**存在可读行 | 删掉回填 ⇒ FAIL（R-V55-107） |
| 队列长度 **恒 ≤ 1**（`TURN_QUEUE_MAX = 1` 单源，SW 侧） | 改成无界 / 2 ⇒ FAIL |
| 排队条目**不丢**：drain 后确实执行了一条（且是同一条文本） | 丢弃队列 ⇒ FAIL |
| 仲裁结果 ∈ **闭集 4 项**：`executed` / `queued` / `busy-rejected` / `ai-deferred` | 出现第五种结果 ⇒ FAIL |

### 3. AI 主动路径（**不排队**，只「不发起 + 留痕」）

```
pressCandidate(opId, value, {by:'ai'})：
  若 state.pending（在飞回合）⇒ 返回 'blocked:busy'
  → 写系统行「AI 主动回合推迟：上一条仍在处理」（**不排队、不重试**）
  → 该候选的**可达 next 仍存在**（用户可点）⇒ 非死端
```

**为什么 AI 不排队**：AI 主动是**可放弃**的建议，不是**用户的输入**。为 AI 排队的队列会与用户的队列竞争，并可能形成
「AI 在用户不知情时插队执行」的观感（打扰控制的反面）。⇒ AI 撞车一律**让位**给用户（`blocked:busy` + 留痕），
且**计入**打扰控制的频次/链深度（不是免费重试）。

### 4. SW / panel 分工（**体积副产物：SW 侧零 sidepanel 字节**）

| 项 | 落点 | 理由 |
|---|---|---|
| 队列本体 / 入队 / drain / 上限常量 | **`background/service-worker.ts`（+ 可能的 `background/turn-queue.ts`）** | `chatBusy` 本就在 SW；队列与「一个在飞回合」是**同一生命周期的两种状态**；⇒ 落 `background.js`（**不计 sidepanel 预算**，v5 先例逐字承认该口径） |
| 队列的**可见留痕**（系统行）与**草稿回填** | 面板 | 流内可见性属面板；`#input` 属面板 |
| 仲裁结果类型 | **两侧同源**：`background/chat-events.ts` 的 payload 类型（type-only 语义，`KIND_SET` **40 不动**） | 避免两侧各写一套字符串 |

### 5. 与 `MAX_OPEN_ASKS` / `pendingOps` 的关系（**零冲突，不改既有仲裁**）

- `pendingOps` FIFO（`pipeline.ts:69-89`）管的是 **op 的 params/consent 卡**（面对 `MAX_OPEN_ASKS = 2`）；
- 本 ADR 的队列管的是 **回合（chat turn）**；两者**互不相交**（一个管卡，一个管回合）；
- 既有语义**一律保留**：`REF_ROUND_PREFIX` 本地回合不入队（op 侧）、`resolvePending` 幂等、`MAX_OPEN_ASKS = 2` 逐字。

## 后果

**正面**
- 「用户输入被静默吞掉」从**不可判**变为**结构性不可能**：三条路径（正常 / 排队 / 明确拒绝 + 草稿回填）覆盖全部输入。
- 单飞语义保留（同一时刻一个在飞回合）⇒ `chatBusy` 的**并发保护价值**不被削弱（不是把单飞删掉）。
- 仲裁结果闭集 4 项可枚举 ⇒ 门禁可穷举断言（含反证）。

**负面 / 代价**
- 面板要处理两个新 payload 变体（`queued` / `busy-rejected`）⇒ `chat-result` 的 union 扩 2 项（type-only）+ 面板 2 条分支（~300 B）。
- 「草稿回填」需要一个**可判**的写点（`#input.value = text`）——若用户在此期间已输入新内容，回填会**覆盖**用户的新输入
  ⇒ 规则：**仅在 `#input` 为空时回填**，否则只留痕并在行文案里附上被拒文本（零明文口径允许：文本是**用户自己的话**，本就出现在 `user` 卡里）。（判据：注入「非空输入 + 拒绝」⇒ 不覆盖 + 行内可见文本。）
- 排队条目在 session 切换时可能指向旧 session ⇒ 沿用既有 `sessionIdAtStart` 纪律：排队条目**绑定起点的 session**，切换后 drain 时以**起点 session** 执行或**明确拒绝 + 留痕**（二选一显式，实现时按此判据落）。
